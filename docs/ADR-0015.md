# ADR-0015: Localized, Evidence-Gated Production Architecture for the Grounded Multiplicity Recursive Cognition Engine

> **Local Identifier:** `ADR-0015` — recursive-cognition local register, succeeding the frozen v3.3 baseline set ADR-001…ADR-014.  
> **Namespace:** `recursive-cognition-local`. No mount-wide or PRISM-global number is asserted; numbering elsewhere in the repository is namespaced and conflicting.  
> **Target Subsystem:** `/run/media/multiplic/AGI/prismagi/mount/SUBSYSTEMS/recursive-cognition`  
> **Implementation Plan:** [`docs/PLAN-ADR-0015.md`](PLAN-ADR-0015.md)  
> **Frozen Baseline:** `Multiplicity-Recursive Cognition Engine.txt` (v3.3 read-only external reference; not a production artifact and not linked because it is not present under `RC_ROOT`)  
> **Reference Architectures:** `kuramoto-prism`, `o3de-prism`, `skip-logic`  
> **Design Class:** `Base` for this governance decision; inherited `Safety-First` obligations from ADR-004, ADR-006, ADR-007, ADR-010, ADR-011, ADR-014; inherited `Deferred` obligations from ADR-005 and ADR-012.

---

## 1. Context and Problem Statement

The v3.3 planning baseline defined the Grounded Multiplicity-Recursive Cognition Engine across four pillars — discrete control barrier functions, spectral telemetry, hybrid stability, and typed meta-cognitive audit — and proposed fourteen local ADRs with a formal-artifact pipeline (LexLean) and a governance/evidence layer (PrismPM). The review that produced it identified one systemic weakness: **claims were asserted but not evidenced**. Five obligations remained open, and the baseline explicitly forbids any "verified" claim until they are closed.

The target directory currently contains only that frozen baseline text. It has no canonical root contract, no pinned toolchain, no harness, no report generator, no release root, and no CI gate. Sibling subsystems (`kuramoto-prism`, `o3de-prism`, `skip-logic`, `production`) already demonstrate the required production pattern: one authoritative 9-suite runner, automated dual reports, fail-closed pre-commit and CI, content-addressed releases, and receipt-linked evidence.

Two constraints shape this decision:

1. **Evidence discipline.** Architecture decisions must name an enforcement site and produce machine-checkable evidence, or be explicitly recorded as a trusted component with residual risk accepted at a phase gate.
2. **Localization.** All production activity for this subsystem must remain physically inside the target folder. Evidence borrowed from another checkout or subsystem is not evidence for this subsystem.

This ADR records the governance decision that makes those constraints binding. It does **not** assert that the implementation exists or that any theorem has been checked.

---

## 2. Decision Drivers

1. **No unsupported verification claim** — every `verified` label must trace to a LexLean attestation or Kani output with an evidence grade of E5 or better.
2. **Fail-closed enforcement** — boundary violations, toolchain drift, missing receipts, and harness failures must abort commits and CI, not produce warnings.
3. **Single source of truth** — one `.lex.tex` source per artifact, one runner, one report pair, one release root; no parallel hand-maintained truth.
4. **Localization by construction** — a canonical root check precedes every other suite, and all config paths are relative.
5. **Reproducibility** — pinned toolchain, checked-in lockfiles, and tool digests make local and CI results comparable.
6. **Parity with proven subsystems** — reuse the 9-suite harness and dual-retention reporting shape rather than inventing a bespoke process.
7. **Honest readiness staging** — PDR / CDR / TRR-1 / TRR-2 gates cannot be passed by documentation alone; open Deferred risks remain visible.
8. **Additive governance** — the frozen v3.3 baseline is not edited or renumbered.

---

## 3. Decision Outcome

### 3.1 Y-statement

> In the context of **production-grade development of the recursive-cognition subsystem from a frozen v3.3 planning baseline**,  
> facing **asserted-but-unevidenced claims, five open verification obligations, and a risk of artifacts leaking outside the subsystem boundary**,  
> we decided for **a localized, evidence-gated production architecture with a pinned toolchain, a 9-suite fail-closed harness, dual reports, content-addressed releases, and named TCB/residual-risk entries**,  
> and against **ad-hoc notes, pasted compiler output, unpinned tools, cross-subsystem evidence reuse, and a "verified" label before TRR-2**,  
> to achieve **traceable, reproducible, audit-ready decisions where no claim outruns its evidence**,  
> accepting **longer commit latency, stricter path/config discipline, and the need to formally supersede ADR-002 if the baseline Lean pin must change**.

### 3.2 Binding decisions

- **D1 — Canonical root.** `RC_ROOT = /run/media/multiplic/AGI/prismagi/mount/SUBSYSTEMS/recursive-cognition`. Every production artifact must resolve below it. Escaping symlinks, hardlinks, and absolute config paths are forbidden (`INV-RC-0015-a`).
- **D2 — Governance phase first.** Phase 0 created only `docs/PLAN-ADR-0015.md` and `docs/ADR-0015.md`. Phase 1 then added the spike sources, config, locks, and evidence strictly inside `RC_ROOT`; the frozen baseline text was not edited.
- **D3 — Evidence before claim.** `VERIFICATION.md` grades every public claim E0–E6. `verified` requires E5+ with a receipt id; pasted output and screenshots are inadmissible (`INV-RC-0015-b`). The Phase 1 attestation is retained as generated stdout plus a PrismPM-linked evidence record, not pasted into prose.
- **D4 — Reproducible toolchain.** `lean-toolchain`, `lexlean.toml`, `lexlean.lock`, `prismpm.toml`, and `tools.lock` are checked in. The baseline pin `leanprover/lean4:v4.32.1` stands historically; ADR-0016 superseded only the Lean pin with `v4.32.2`, and ADR-0017 closes D4's blocked-verify clause with governed Prism model content. No release claim follows from the passing verify (`INV-RC-0015-c`, `RISK-TOOLCHAIN-DRIFT`).
- **D5 — Formal core in LexLean.** The DT-CBF, spectral, hybrid-stability, and trace artifacts are single-source `.lex.tex` modules. Tier-1 modules are Mathlib-free and prefer exact rational/integer encodings over floating point (`INV-RC-0015-d/e/f`).
- **D6 — TCBs are named, not hidden.** `m_inter_bounds_drift` is a single declared deferred axiom tied to `RISK-MINTER`; OSQP sits behind a residual-checking wrapper with a 2.5 ms watchdog tied to `RISK-OSQP` (`INV-RC-0015-g`).
- **D7 — One runner, dual reports, fail-closed gates.** `run_tests.py` drives TS-01…TS-09, including domain sub-suites and the four Kani harnesses. Pre-commit and CI run the same harness and abort on any failure. Reports are retained as timestamped snapshots plus canonical `LATEST` files with a stable SHA-256 fingerprint (`INV-RC-0015-h`).
- **D8 — Release locally, evidence-complete.** PrismPM publishes only to `production/build/<sha>/` under `RC_ROOT`. TRR-2 requires all Safety-First ADRs to have passing receipts and all Deferred ADRs to have signed residual-risk acceptance.

## 4. Alternatives Considered

| Option | Why rejected |
| :--- | :--- |
| Keep governance in the baseline text file and add notes inline | The baseline is frozen; inline notes create drift and cannot be machine-checked or linked to evidence. |
| Use a mount-wide/global ADR number by guesswork | No authoritative mount-wide allocator exists; numbering is namespace-local and already collides elsewhere. A wrong number creates false lineage. |
| Develop in a shared workspace and copy "verified" artifacts into the subsystem at release | Breaks provenance and localization; evidence from another root does not attest this root. |
| Paste `lexlean verify` and `cargo kani` output into reports | Unfalsifiable; the baseline review identified exactly this failure mode (ADR-014). |
| Rely on manual review plus a single `verify.sh` | No fail-closed gate, no dual reports, no drift detection; sibling subsystems already demonstrate the stronger pattern. |
| Upgrade to the latest available Lean toolchain (4.32.2) because siblings use it | Would silently supersede ADR-002; any change requires an explicit spike and superseding ADR. |
| Prove `m_inter_bounds_drift` inside this phase with whatever is available | Would fabricate a continuous real-analysis result; ADR-005 correctly keeps it as a TCB hypothesis. |
| Write production artifacts under `SUBSYSTEMS/production/` because that folder is named "production" | That is a different subsystem with its own canonical root; all production here must remain under `RC_ROOT`. |

## 6. Consequences

### Positive

- Every decision has a named enforcement site; "we decided X" is no longer the end of the record.
- Evidence is generated, fingerprinted, and retained in two forms, eliminating documentation drift and pasted-claim risk.
- Localization is checked before any other verification, so cross-subsystem contamination fails early and loudly.
- Deferred items stay visible as signed risks rather than disappearing into prose.
- The subsystem inherits the proven harness/report/CI shape of its siblings without inventing new process.

### Negative / Trade-offs

- Commit latency increases because the full harness and attestation run in pre-commit and CI.
- Configuration must use relative paths and pass a canonical-root audit; convenience absolute paths are rejected.
- The baseline Lean pin may need a formal supersession if the spike shows it is unusable; that cost is deliberate and visible.
- Documentation-only Phase 0 adds a gate before code can be written.
