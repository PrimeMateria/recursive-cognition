The v3.3 planning baseline established *what* to build and *why* each safety argument is conditional. This ADR plan addresses *how* to build it with an auditable decision trail, using **LexLean** for the single-source formal-artifact pipeline and **PrismPM** for the governed execution and evidence register. It is deliberately scoped to close the gap that surfaced repeatedly in the review: claims that were asserted but not evidenced.

---

# ADR Plan — Grounded Multiplicity-Recursive Cognition Engine (v3.3 → Verified Prototype)

## 1. Tooling role definition

| Tool | Role in this project | What it replaces | Primary evidence output |
|---|---|---|---|
| **LexLean** | Single-source LaTeX-to-Lean 4 compiler. The DT-CBF theorems, the `m_inter_bounds_drift` TCB hypothesis, the spectral-binning invariants, and the dwell-time lemma are authored once in a closed-lexicon `.lex.tex` source. LexLean generates the canonical document *and* the prose-free Lean module from the same IR, then `lexlean verify` runs the pinned `leanprover/lean4:v4.32.1` toolchain, replays with `leanchecker`, audits axioms via `#print axioms`, and publishes a content-addressed attestation. | Hand-maintained Lean files + separate LaTeX spec that drift apart; unverifiable "paste the compiler output" claims. | `CONFORMANCE.md`, `VERIFICATION.md`, tamper-evident attestation per release. |
| **PrismPM** | Project portfolio management layer. Hosts the ADR register as governed decision objects, the RAID log for formal-verification risks (the five open obligations), phase-gate management (PDR/CDR/TRR) for the prototype upgrade, resource allocation across Lean/Rust/Kani workstreams, and the roll-up risk register that maps each ADR to its mitigation. | Scattered notes, ad-hoc tracking, unlinked obligations. | Phase-gate exit criteria, risk register roll-up, ADR↔task↔evidence traceability. |

**LexLean is an unconventional choice and must itself be governed by an ADR.** It is at v0.4, does not claim the full 1.0 specification, and parts of its own compiler are written in LexLean and pass its own checks. That is good evidence of dogfooding, not evidence of fitness for this domain. ADR-001 below makes that risk explicit and gates adoption behind a conformance spike.

## 2. ADR methodology

Adopt the **Y-statement model** (Zdun et al.) for lean ADR capture, and the **five-phase ADR lifecycle** — Capture, Context, Decide, Record, Link — with three refinements taken from safety-critical ADR practice:

1. **Every ADR names its enforcement site.** Not just "we decided X," but "X is enforced at `<artifact>` and verified by `<harness/theorem>`, or it is a TCB hypothesis with residual risk logged in PrismPM".
2. **Every ADR carries a Design Class** — `Safety-First` (proof required), `Base` (Lean proofs sufficient), or `Deferred` (explicitly trusted, not proven). This mirrors the "proof budget scales with structural complexity" pattern.
3. **Every ADR is a PrismPM object, not a file.** The ADR text lives in the repository; its status, owner, linked risk, linked phase-gate, and linked LexLean module are governed in PrismPM. A decision that is not linked is not made.

### ADR template (Y-statement + enforcement)

```markdown
# ADR-NNN: <short imperative title>

## Y-statement
In the context of <use case / component>,
facing <concern / force>,
we decided for <option>
and against <alternatives>,
to achieve <quality / goal>,
accepting <downside / risk>.

## Design class
Safety-First | Base | Deferred

## Enforcement site
- LexLean module: `<path>.lex.tex`
- Lean theorem: `theorem <name>`
- Kani harness: `<path>#<harness>`, unwind bound N = <n>
- Runtime component: `<crate>::<module>::<fn>`
- If Deferred: TCB component, residual risk ID in PrismPM

## Consequences
- Positive:
- Negative:
- Residual risk (PrismPM risk ID):

## Links
- Supersedes / superseded by:
- Related ADRs:
- Phase gate: PDR / CDR / TRR
```

## 5. Implementation sequence

**Phase 0 — ADR capture (1 week).** Draft ADR-001 through ADR-014 in PrismPM. Assign Design Class and enforcement site to each. No code yet.

**Phase 1 — LexLean conformance spike (2–3 weeks).** Encode three representative artifacts in `.lex.tex`: a `Rat`-order helper lemma, the `dt_cbf_forward_invariant` statement, and the `prime_bin_partition` invariant. Run `lexlean verify`. Record the attestation in PrismPM. **ADR-001 is accepted only if all three verify and the attestation is reproducible.**

**Phase 2 — Formal Core (4–6 weeks).** Move the discrete CBF, spectral, and hybrid-stability modules into LexLean. Each module is an ADR enforcement site. The `m_inter_bounds_drift` axiom is declared in the LexLean source with an explicit `@[deferred]` annotation and a PrismPM risk link.

**Phase 3 — Runtime harnesses (3–4 weeks).** Kani harnesses for REQ-SAF-01, REQ-OPT-01, REQ-HYB-01, REQ-AUD-01. Each harness attaches its real `cargo kani` output to the PrismPM task; no pasted claims accepted (this is the ADR-014 gate).

**Phase 4 — TRR-2 evidence assembly (2 weeks).** LexLean attestations + Kani outputs + risk acceptances roll up into the TRR-2 evidence bundle. The prototype is declared "verified prototype" only when every Safety-First ADR has a passing receipt and every Deferred ADR has a signed residual-risk acceptance.

---

## 6. What this plan deliberately does not do

- It does **not** claim LexLean replaces Mathlib for the `m_inter` proof. ADR-005 keeps that as a TCB hypothesis until a real-analysis proof exists. LexLean proves the *discrete algebraic* layer; it does not fabricate the continuous layer.
- It does **not** treat PrismPM as a source of truth for correctness. PrismPM is the governance and evidence-linking layer; the correctness evidence is the LexLean attestation and the Kani output.
- It does **not** upgrade readiness. v3.3 remains the planning baseline until TRR-2 passes with real evidence.

## 7. Immediate next action

Draft **ADR-001** and run the LexLean conformance spike. If `lexlean verify` produces a reproducible attestation for the three spike artifacts, ADR-001 is accepted and Phase 2 begins. If it does not, ADR-001 is rejected and the fallback (hand-maintained Lean + CI-pinned toolchain) is recorded as a superseding ADR. Either outcome is evidence, which is the point.
