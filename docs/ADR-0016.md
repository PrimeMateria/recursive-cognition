# ADR-0016: Supersede the Baseline Lean Pin with LexLean 0.4.3 and Lean v4.32.2

> **Local Identifier:** `ADR-0016` — recursive-cognition local register, succeeding local ADR-0015.  
> **Namespace:** `recursive-cognition-local`. No mount-wide or PRISM-global ADR number is asserted.  
> **Target Subsystem:** `/run/media/multiplic/AGI/prismagi/mount/SUBSYSTEMS/recursive-cognition`  
> **Supersession scope:** This ADR supersedes **only** the Lean toolchain pin in ADR-002. The Mathlib exclusion for Tier-1 modules remains in force.  
> **Governing Plan:** [`docs/PLAN-ADR-0015.md`](PLAN-ADR-0015.md)  
> **Frozen Baseline:** `Multiplicity-Recursive Cognition Engine.txt` (v3.3 read-only external reference; not a production artifact and not linked because it is not present under `RC_ROOT`)  
> **Design Class:** `Base` governance decision with inherited `Safety-First` reproducibility obligations.

---

## 1. Context and Problem Statement

ADR-0015 §11 recorded a reproducible LexLean 0.4.0 attestation under the baseline pin `leanprover/lean4:v4.32.1`, but also recorded a hard governance blocker: installed PrismPM 0.5.0 rejects that pin because LexLean 0.4.3+ requires the security-patched `leanprover/lean4:v4.32.2`. The relevant upstream change is a **breaking security update**: Lean 4.32.2 fixes the nested-inductive kernel soundness issue [leanprover/lean4#14576](https://github.com/leanprover/lean4/issues/14576). Continuing to verify production evidence on 4.32.1 would knowingly retain a patched kernel defect.

ADR-0015 explicitly required that any change to the baseline pin be made through an **explicit spike and superseding ADR**, not by silently editing `lean-toolchain`. This ADR records that spike and decision.

Two further constraints were discovered during the spike:

1. LexLean 0.4.4 moved every identity to BLAKE3 UOR κ-labels and raised the project/lock/attestation schemas; LexLean 0.4.5 adds Nat arithmetic laws but still requires `lexlean/project/2`.
2. PrismPM 0.5.0 — including the newest available PrismPM source line — still embeds LexLean 0.4.3 and refuses `lexlean/project/2` with `LLC0103: unsupported project schema`. Adopting 0.4.5 would therefore replace the original pin conflict with a governance-check conflict.

The decision is therefore **not** simply “use the newest crate”. It is “use the newest verifier that closes the security pin conflict while preserving the governed toolchain contract”.

---

## 2. Decision Drivers

1. **Kernel security** — do not publish evidence produced by a toolchain with a known patched soundness defect.
2. **Evidence continuity** — the ADR-001 attestation remains historical evidence; a new attestation must be reproduced under the new pin before the pin changes.
3. **Governance compatibility** — `prismpm check` must pass against the same project configuration that `lexlean verify` uses.
4. **Format stability** — avoid a schema migration that no installed governance tool can read.
5. **No silent drift** — ADR-002 is superseded explicitly, with rationale, alternatives, rollback, and retained outputs.
6. **Honest scope** — a passing static check is not a release, and full `prismpm verify` is not claimed.
7. **Localization** — all decision, evidence, lock, and report artifacts remain below `RC_ROOT`.

---

## 3. Decision Outcome

### 3.1 Y-statement

> In the context of **recursive-cognition production evidence governance from a frozen v3.3 baseline**,  
> facing **a security-patched Lean pin required by modern LexLean, an original PrismPM pin conflict, and a newer LexLean release that PrismPM cannot read**,  
> we decided for **superseding only the ADR-002 Lean pin with `leanprover/lean4:v4.32.2` and adopting LexLean 0.4.3 as the canonical verifier**,  
> and against **keeping Lean 4.32.1, adopting LexLean 0.4.5, or silently editing the pin**,  
> to achieve **kernel-security-correct, reproducible attestations that PrismPM 0.5.0 can still govern**,  
> accepting **regeneration of the Phase 1 attestation, a bounded toolchain migration record, and a remaining release-model gap unrelated to the pin**.

### 3.2 Binding decisions

- **D1 — Lean pin superseded.** `lean-toolchain` and `lexlean.toml:lean_toolchain` are set to `leanprover/lean4:v4.32.2`. ADR-002's Mathlib exclusion is unaffected.
- **D2 — Canonical verifier.** `lexlean 0.4.3` at the digest recorded in `tools.lock` is the only verifier whose output may support a current `verified` claim for this subsystem.
- **D3 — Historical evidence retained.** The ADR-001 attestation `7998182e99ca10aa0a3cff41b2ebb90c846bf0f7fb8fe6a0b2f93efeea4aa8ca` remains valid as a historical record of the 0.4.0/4.32.1 spike. It is not the current production attestation.
- **D4 — Current attestation.** The canonical attestation is `e2ea04e5e9c899c49fb341ecf555e205208d2e32489e0bf86e2fb57851069bb7` (`lexlean/attestation/2`), reproduced on a repeat run and after `lexlean clean`.
- **D5 — Governance format frozen at readable schemas.** `lexlean/project/1` and `lexlean/lock/2` remain the canonical project and lock schemas because PrismPM 0.5.0 can read them. LexLean 0.4.4/0.4.5 BLAKE3 schema migration is recorded as a rejected alternative, not adopted.
- **D6 — PrismPM static check passes.** `prismpm 0.5.0 check` passes with semantic ID `e3ca15a8cc6700d45fbd6d8a6548ea43070e3b7e63655749f827f9ab95ab11f1`, matching the LexLean semantic ID.
- **D7 — Release not claimed.** Full `prismpm verify` now fails with `PP5003: LexLean snapshot contains no Prism declarations`; this is a model-content gap in the spike, not a toolchain pin conflict. No release or `verified prototype` claim follows from this ADR.
  > **Superseded in part by [ADR-0017](ADR-0017.md):** D7 remains the historical record of that blocker. Real `prismpm verify` now passes under the governed stack with attestation `7963a1eb1ee4462fd5c87a7c1b2bc430dbbb2f8d0774b5dc606e43a0b2a66c71`; the old ADR-0016 attestation remains historical. Release, Kani, nine-suite, and TRR-2 claims are still not made.

## 5. Alternatives Considered

| Option | Result | Disposition |
| :--- | :--- | :--- |
| Keep Lean 4.32.1 / LexLean 0.4.0 | Original spike verifies, but PrismPM 0.5.0 refuses the pin (`LLC0101`) and the kernel defect remains unpatched. | **Rejected.** |

## 7. Consequences

### Positive

- The production evidence toolchain now uses the security-patched Lean kernel.
- The original PrismPM pin conflict is resolved without changing governance schemas.
- The current attestation is reproducible and bound to unchanged spike sources.
- Tool identity, incompatibility history, and rejected alternatives are explicit in `tools.lock`.

### Negative / Trade-offs

- The Phase 1 attestation cited throughout ADR-0015 is now historical; current references must use the new digest.
- LexLean 0.4.4/0.4.5 improvements (BLAKE3 identities, Nat arithmetic laws, arrays, lean-modules/snapshot commands) are deferred until PrismPM can consume their formats.
- `tools.lock` now records three LexLean versions; automated checks must select by `status = "canonical"`, not by highest version.

### Residual risks

| Risk ID | Residual risk | Acceptance gate |
| :--- | :--- | :--- |
| `RISK-TOOLCHAIN-DRIFT` | Pin migration performed; drift still possible if tools are replaced without updating `tools.lock`. | Every commit via TS-01…TS-03 (Phase 4 gate) |
| `RISK-LEXLEAN-IMMATURITY` | LexLean 0.4.x is pre-1.0; conformance is bounded to the spike. | CDR evidence already retained; revisit at TRR-2 |
| `RISK-LEXLEAN-GOVERNANCE-LAG` | PrismPM still embeds LexLean 0.4.3 and cannot read newer schemas. | Re-evaluate when a PrismPM release embeds ≥0.4.4 |
| `RISK-PRISM-MODEL-GAP` | `prismpm verify` needed Prism declarations absent from the spike. | Closed for the governed verify path by ADR-0017; future model changes require fresh attestations |

## 8. Rollback

1. Restore `lean-toolchain`, `lexlean.toml`, and `lexlean.lock` from the ADR-001 spike state recorded in [`production/evidence/ADR-001-lexlean-spike.json`](../production/evidence/ADR-001-lexlean-spike.json).
2. Set `tools.lock` canonical status back to LexLean 0.4.0 / PrismPM 0.4.0.
3. Re-run the original verify command and require attestation `7998182e99ca10aa0a3cff41b2ebb90c846bf0f7fb8fe6a0b2f93efeea4aa8ca`.
4. Do **not** delete this ADR or its evidence; record the rollback reason in a superseding record.

Rollback reintroduces the known kernel defect and the PrismPM `LLC0101` conflict; it is an emergency path only, not a preferred state.
